## Exact prepared corrections

1. [Fault API-only writes](../../supabase/proposals/retail_fault_api_only_writes.sql): revoke only direct PUBLIC/anon/authenticated table and column INSERT/UPDATE/DELETE on batches, tickets and updates. Batch deletion matters because it can cascade. Preserve SELECT, existing RLS/restrictive demo guards and service-role CRUD needed for existing imports/failed-import cleanup. Effective inherited writes cause an exception and transaction rollback. The new Save RPC supplies atomic update/audit; authenticated clients cannot forge/delete its history directly.
2. [Legacy Deep Cleaning isolation](../../supabase/proposals/retail_legacy_cleaning_evidence_isolation.sql): four restrictive storage policies AND with the old permissive policies. Scope is this legacy bucket's `employee/date/deep_cleaning/submission/file` paths; other activity paths/buckets retain their current behavior. Require uniquely mapped active auth identity matching the stored owner and exact source/date/path. Existing Operations Manager/Admin owners retain their own-record access; this does not grant new authoring roles, because existing permissive policies remain an upper bound. Non-owner Admin review uses the scoped backend evidence route, not unrestricted direct bucket access.
3. New additive source/upload guards prevent owner/path/type relabelling, another owner's metadata insertion, and mutations after final submission or schedule linkage. A submitted record with `pending_images=true` remains writable while before/after files arrive. Clearing that flag requires the expected upload roles, exact identity/path, private bucket and matching stored-object size. Existing finalized incomplete records are not rewritten. Training rows return immediately to their original guards; no Training permission, function or trigger is changed.
4. An additive storage trigger locks the source row and checks its latest state on physical writes, closing the status-finalization race that RLS alone could leave. Update checks both old/new paths. Submitted/linked objects cannot be overwritten, moved, upserted or deleted through ordinary owner operations. Trusted service-role writes also cannot alter sealed evidence through this trigger. No existing storage policies/triggers are dropped.

The evidence proposal is intentionally a once-only transaction using CREATE, not silent CREATE OR REPLACE. It fails on existing new object names, public bucket, drift of the exported Training guard, unexpected legacy policy names/roles, or insufficient storage-owner authority. A failed preflight rolls back before creating controls. Do not escalate/grant owner permissions automatically to make it run.
