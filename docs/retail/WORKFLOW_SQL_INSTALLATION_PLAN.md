### Additional gate: existing direct Fault Tracker table access

Baseline migration 018 grants authenticated CRUD with manager policies on tickets and history, and state reads based on imported state. The new proposals do not replace those policies. If still effective, direct REST/table access can bypass the backend's canonical Store Code envelope, mutate history or insert a claimed workflow marker. Resolve any such bypass through a separately reviewed narrow policy/trigger design before declaring a release PASS; preserve source rows and existing import service behavior. Do not silently revoke existing operational permissions in this readiness task.

## Rollback and data preservation

- Before any proposal transaction commits, ROLLBACK restores its DDL. After a commit, freeze the new mutation endpoints first: revoke EXECUTE on `rpc_retail_fault_update(...)` and `rpc_retail_cleaning_link_fo(...)` from service_role in an authorized transaction. This does not revoke the source reader used by existing linked reports. Backends must fail closed; the UI may still display Update until capability is disabled/refreshed.
- To hide Fault Tracker mutation availability, restore the captured capability definition or remove its service execution while investigating. Preserve the read helpers when legitimate linked records already exist.
- Roll back application code through GitHub main and Railway auto-deployment to the recorded compatible prior SHA. Preserve unrelated main changes. SQL installation alone did not deploy code.
- Do not delete ticket updates, undo approved completions, reset schedule metadata or drop source/history tables. If no new records exist and no older routines existed, an approved DDL rollback may drop the new writer then its capability, cleaning writer then reader, and the new index; inspect dependencies without CASCADE. If routines existed, restore their captured definitions/owners/ACLs instead. If legitimate records exist, retain compatible readers and reconcile through an authorized operational correction.
- A security rollback must **not restore known broad evidence exposure**. Retain the approved restrictive protection; if it breaks legitimate FO work, stop new writes and seek the approved corrected policy, with the exact captured original definition retained as evidence rather than automatically reinstated. Previously issued signed links can remain usable until expiry (new reporting links: 600 seconds); immediate containment needs the approved storage incident procedure, not deleting evidence.
- Production backup/PITR is a recovery option requiring explicit incident authorization; do not restore a database and erase unrelated operations as a routine SQL rollback.
